# **Performance**

The measured numbers: which ids matisse's encoder gives on real corpora beside tiktoken, Hugging Face tokenizers and
GitHub's bpe crate, how fast each of them encodes on one core, on short prompts and across all cores, and where
matisse's own single-core encoding spends its time. [design.md](design.md) holds the decisions the encoder rests on.
Every table of measurements below is generated by a script from the outputs of one collection, begun on 2026-10-20 and
timed at commit 97aa503; the probe's run on enwik9 named below is the exception, and the figures in the prose are read
from the tables and from the archived outputs.

## **The programs**

Two programs in tools/probes measure matisse. `matisse_corpus` is the third layer of the test strategy: on GPT-2's and
cl100k's pinned vocabularies it holds the ids of `encode()` on a corpus to the known-answer fixture's digest where the
fixture names the corpus, to the ids of every piece merged with no cache, and `decode()` to the text; for both
inventories it holds `encode_parallel()` to `encode()` at 2, 4, 8, 12, 16 and 24 chunks, at the chunkings of 4,096 and
65,536 code points and at one chunk per byte, and at every cut of that last chunking it holds the pieces a worker keeps,
its chunk and the right context segmented as a complete input, to the serial pieces. `encode_parallel()` runs one thread
per chunk, so a chunk count past 32,768 is skipped with a line saying so, and the cut check covers it alone; a thread
per chunk at every cut of `munch-cpp@15b2863c` under cl100k's factorization inventory, 559,642 chunks, fails on this
machine with `std::system_error` when a thread cannot be started. On enwik9 the 4,096-code-point chunking is 243,535
chunks, and 136,695,218 to 148,173,524 cuts per tokenizer and inventory are checked. The probe prints each corpus's ids
line, the count and the SHA-256 of the ids as little-endian 32-bit words, which every other encoder's ids are compared
by, and the certified-anchor supply.

`matisse_bench` times `encode()`, the same encoding with no cache, the segmentation alone, one call per prompt, with a
piece cache of its own and with one cache kept across the calls, `encode_parallel()` at each worker count on one long
text and `encode()` over a batch of documents spread over a pool of threads that each take the next document from a
shared counter and keep one cache across the documents they take. Every row runs one pass that warms the caches and
gives the result every timed pass must reproduce; that pass is held to `encode()`'s ids in the rows of the encoding with
no cache, of the prompts with a kept cache, of `encode_parallel()` and of the batch, and every mode prints the ids line
of `encode()`, so no figure is taken of an encoding other than the one whose ids are compared. Both programs run as
CTest entries when `-DMATISSE_VOCAB_DIR` names the vocabulary directory, the bench for one pass of the single mode's
rows on the validator's sample, and `-DMATISSE_CORPUS_DIR` adds the probe on the three corpora of the test strategy.

The other encoders run from harnesses kept beside the corpora outside the repository, so that nothing a vendor ships
enters it, and print rows and ids lines in the same format:

- tiktoken 0.14.0 and numpy 2.5.4 from PyPI, under Python 3.12.3. Its encodings are built by its own `openai_public`
  constructors from the pinned rank files, served through `TIKTOKEN_CACHE_DIR` and held there to the digests tiktoken
  pins; Llama 3's is built from llama3.tiktoken with the pattern of Meta's tokenizer.py. A long text is timed through
  `encode_to_numpy(text, disallowed_special=())`, the Rust core's encoding returned as one buffer with no Python list,
  the text a Python string before the clock starts. A prompt is timed through `encode_ordinary()`, the per-call
  interface, its Python list included. A batch is `encode_ordinary_batch(documents, num_threads=N)`, which maps
  `encode_ordinary()` over the documents on a `ThreadPoolExecutor` of N threads, given 10,000 documents a call, the time
  summed over the calls; its Rust binding encodes with the interpreter lock released and returns the ids as a Python
  list.
- Hugging Face tokenizers 0.23.3 from PyPI, loading the tokenizer.json of each tokenizer, pinned by the digests below,
  with `encode_special_tokens` set so that a special token's spelling is text, as in the other encoders. A long text and
  a prompt are timed through `encode(text, add_special_tokens=False)`, which builds the whole `Encoding` with its tokens
  and offsets. A batch is `encode_batch()` with `RAYON_NUM_THREADS` set to the thread count, whose binding encodes the
  documents in parallel with the interpreter lock released, given 10,000 documents a call as tiktoken is. The
  Xenova/gpt-4 conversion carries cl100k's pattern as tiktoken shipped it before its possessive rewrite.
- bpe 0.2.3 and bpe-openai 0.3.2 from crates.io, built with Rust 1.99.1 at opt-level 3 with link-time optimization and
  one codegen unit, the versions pinned by the harness's Cargo.lock. cl100k and o200k are bpe-openai's own tokenizers,
  whose bundled rank files have the pinned files' SHA-256; GPT-2 is built from GPT-2's ranks as tiktoken reads them,
  whose SHA-256 is tiktoken's r50k_base digest, under GPT-2's pattern with its look-ahead written as bpe-openai writes
  cl100k's. Llama 3 is left out, since the crate requires every token to encode to itself and 588 of Llama 3's do not,
  as design.md counts them. Every call is `Tokenizer::encode()`, and a batch is the same pool of threads as matisse's,
  written in the harness.

## **The machine**

An Intel i9-12900K with 47 GiB of memory, under WSL2 (Linux 6.18.54.1-microsoft-standard-WSL2, Ubuntu 24.04.4). Its 8
performance cores of two threads and 8 efficiency cores, 24 logical processors, appear to WSL2 as 12 cores of two
threads, and WSL2 exposes no CPU frequency governor. matisse is built with GCC 13.3 at `-O2`, the repository's Release
flags. The machine was otherwise idle for the whole collection, and the timing passes ran back to back. Every
single-thread row ran under `taskset -c 2`; under WSL2 that pins the process to one virtual processor, which Hyper-V may
place on any host core, performance or efficiency, so the single-thread figures carry that spread, and the parallel rows
ran unpinned. The corpora are read into memory before any clock starts. The figures compare within this collection;
rerun on your own machine before quoting any of them.

## **Exactness**

Every encoder's ids were compared by digest on every corpus it ran on, and none differs; the ids on the prompts, the
mixed file and the pages, and matisse's on the three corpora of the test strategy, come from the ids lines of the timed
runs. matisse's ids on the three corpora of the test strategy are the known-answer fixture's. Hugging Face could not
encode enwik9 whole, its process killed with 46 GiB resident while it built the `Encoding`, and was not run on the mixed
file, twice that size; its ids of enwik9's pages, concatenated, have enwik9's digest, so every page begins at a piece
boundary of both patterns, and the batch covers enwik9. For o200k and Llama 3 every other encoder that ran agrees on
every corpus as well. Each engine carries Unicode tables of its own and matisse pins Unicode 15.0.0, and on these
corpora the difference changes no id.

## **Profile**

matisse's encoding on one core, sampled by `perf record -e cpu-clock -F 4999 --call-graph fp` (WSL2 exposes no hardware
counters, so the event is the kernel's clock) while `matisse_bench parallel` ran `encode()` and `encode_parallel()` at
one chunk, four timed passes each, on a build of 97aa503 with `-g -fno-omit-frame-pointer` added to the Release flags.
WSL2's perf is built without the libraries that name symbols, so the shares are computed from the raw stacks named by
`addr2line` with inline frames: only the samples whose stack passes through `Encoder::encode` or
`Encoder::encode_parallel` are kept, and each is assigned to the first component met from the leaf outward. Per cent of
those samples:

| Component | gpt2 `gutenberg` | gpt2 `munch-cpp@15b2863c` | gpt2 `wiki-zh` | cl100k `gutenberg` | cl100k `munch-cpp@15b2863c` | cl100k `wiki-zh` |
|---|---:|---:|---:|---:|---:|---:|
| classes_of | 35.4 | 41.4 | 20.0 | 49.6 | 57.5 | 11.4 |
| segmenter loop | 19.0 | 25.2 | 7.5 | 11.7 | 14.5 | 2.0 |
| DFA walk | 8.2 | 11.0 | 2.4 | 4.8 | 7.0 | 0.5 |
| gate check | 0.5 | 0.6 | 0.2 | 0.4 | 0.4 | 0.1 |
| merge | 19.8 | 4.6 | 51.6 | 26.8 | 14.8 | 76.3 |
| whole-piece lookup | 1.8 | 2.1 | 1.4 | 1.6 | 2.2 | 0.6 |
| piece cache | 7.3 | 6.0 | 5.2 | 2.0 | 1.0 | 3.1 |
| id output | 6.6 | 8.5 | 7.0 | 2.2 | 2.2 | 3.2 |
| allocation | 1.5 | 0.6 | 4.7 | 0.8 | 0.4 | 2.7 |

The components: `classes_of` decodes UTF-8 and finds every code point's class by a binary search in each Unicode set in
turn and the class symbol's index by a search of the symbols; the segmenter loop is the `Segmenter`'s walk of the class
string, the alternatives tried in order; the DFA walk is the munch `Simulator` stepping an alternative's automaton; the
merge is `Merger::merged()`, whose rank of a candidate pair under tiktoken's rule is the id of the two parts'
concatenation, found by hashing the bytes of the concatenation in a map keyed by spelling; the piece cache is
`Piece_cache`'s lookups and stores; the id output is `Encoder::encode_chunk`'s own frame and its vector operations. On
prose and code `classes_of` takes 35 to 58 per cent of the encoding and the segmentation around it, the loop, the DFA
walk and the gate checks, another 17 to 37. On Chinese under cl100k the merge takes 76 per cent, and 45 to 48 per cent
of all the samples end in a hash table's lookup of a spelling, the search, the hash of the bytes and the bucket's index,
the piece cache's table taking at most the 3.1 points of its share and the merge's map the rest.

## **Reproducing**

The corpora are built by `make_corpora.py fetch` and `derive` in the corpus directory, whose README is the recipe, and
the harnesses, their lock files, the collection script and the scripts that read its outputs into these tables are kept
beside them. The matisse side, with `VOCAB` the directory of the pinned vocabulary files, `CORPORA` the small corpora
and `LARGE` the GB-sized ones:

```
$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DMATISSE_VOCAB_DIR=VOCAB -DMATISSE_CORPUS_DIR=CORPORA
$ cmake --build build -j 8
$ ctest --test-dir build --timeout 300 -R 'matisse_corpus|matisse_bench'
$ ./build/tools/probes/matisse_corpus VOCAB CORPORA/gutenberg.txt CORPORA/wiki-zh.txt LARGE/enwik8
$ taskset -c 2 ./build/tools/probes/matisse_bench single VOCAB gpt2,cl100k 15 CORPORA/twitter.json
$ taskset -c 2 ./build/tools/probes/matisse_bench prompts VOCAB gpt2,cl100k 5 CORPORA/prompts.txt
$ ./build/tools/probes/matisse_bench parallel VOCAB gpt2,cl100k 3 LARGE/enwik9
$ taskset -c 2 ./build/tools/probes/matisse_bench batch VOCAB gpt2,cl100k 3 LARGE/enwik9-pages.nul 1
$ ./build/tools/probes/matisse_bench batch VOCAB gpt2,cl100k 3 LARGE/enwik9-pages.nul 24
```

The other encoders' rows come from the harnesses, `vendors.py MODE TOKENIZERS PASSES FILE [THREADS]` for tiktoken and
Hugging Face, with `RAYON_NUM_THREADS` set to the thread count and `VENDORS` naming which of the two run, and
`vendor_bench MODE TOKENIZERS PASSES FILE [THREADS]` for the bpe crate, each reading the vocabulary files from the paths
it names; their `digests TOKENIZERS FILE...` mode prints the ids lines alone, and the whole collection is one script,
`campaign.sh`, which records the machine first as munch's `collect.sh` does. The profile is

```
$ taskset -c 2 perf record -e cpu-clock -F 4999 --call-graph fp -o run.data \
      ./build/tools/probes/matisse_bench parallel VOCAB cl100k 4 CORPORA/wiki-zh.txt 1
$ perf script -i run.data -F ip,dso,dsoff | python3 -I profile_share.py
```

on a build configured with `-DCMAKE_CXX_FLAGS="-g -fno-omit-frame-pointer"`, `profile_share.py` beside the harnesses.
